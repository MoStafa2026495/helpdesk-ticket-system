# Helpdesk: support ticket system (demo)

A small full-stack support desk. Customers open tickets and talk to staff. Agents work a queue with priorities and SLA deadlines. Admins manage staff and read the audit log.

**Stack:** React 19, TypeScript, Vite, Tailwind v4 (front end) · Node 22 + Express 5 (REST API) · SQLite through the built-in `node:sqlite` (database).

## Honest notes

- Personal portfolio project developed with AI assistance (Instinct, an AI assistant). Most of the code was generated by the assistant. The owner is learning it using the walkthrough in `WALKTHROUGH.ar.md`.
- It is a demo: fictional seed data, no real users, no real customer data, not deployed.
- The database is SQLite (one file). Moving to Postgres would change `server/db.ts` and the SQL in `server/app.ts`.

## What it does

| Role | Can do |
|---|---|
| Customer | Sign up, open tickets, see only their own tickets, reply, close, reopen a resolved ticket. Never sees internal notes or the audit trail. |
| Agent | See all tickets, filter/search, reply publicly or add internal notes, change status along allowed steps, set priority, take a ticket for themselves. |
| Admin | Everything an agent does, plus assign tickets to anyone, create staff accounts (API), read the global audit log. |

Product rules (the interesting part, see `src/lib/policy.ts`):

- **Status flow.** open → in progress / waiting for customer / resolved; resolved → closed or reopened; closed is final. Customers can only close, or reopen a resolved ticket. Illegal jumps return 422.
- **SLA deadlines.** Each ticket gets a due time from its priority (urgent 4h, high 8h, normal 24h, low 72h), recomputed when priority changes. "Overdue" = not resolved/closed and past due.
- **Customer reply** moves a "waiting for customer" ticket back to the agent (or the queue if unassigned) and reopens a resolved one.
- **Audit log.** Every create, status, priority, assignment and reply is written in the same transaction as the change. The table is append-only: database triggers refuse UPDATE and DELETE.
- **Conflict detection.** Every ticket has a `version`. Edits must send the version they saw; a stale one gets 409 instead of silently overwriting a colleague.
- **Privacy.** A customer asking for someone else's ticket gets 404, not 403, so ticket ids can't be probed.
- **Auth.** scrypt password hashes, random bearer tokens (only the SHA-256 is stored), 7-day expiry, login rate limit (5 wrong passwords per IP+email per 15 min), sign-up rate limit. Public sign-up can only create customers.

## Run it

Needs Node 22.5+.

```
npm install
npm run build
npm run seed      # fictional demo data into ./data.sqlite
npm run server    # http://localhost:3000
```

Demo logins (password `demo-password-1`): `maya@customer.test` (customer), `sam@demo.test` (agent), `admin@demo.test` (admin). Development with reload: `npm run server` and `npm run dev` (Vite proxies `/api`).

Env: `PORT`, `DB_FILE`, `TRUST_PROXY=1` behind a reverse proxy.

## Tests

```
npm test               # Vitest: business rules in src/lib/policy.ts
npm run test:server    # node:test: API on a real HTTP server, in-memory SQLite (24 tests)
npm run typecheck:server
```

The API tests cover role permissions, customer isolation, internal-note privacy, status flow, SLA recompute, version conflicts, assignment rules, audit trail and append-only enforcement, search/filter/pagination, SQL-injection text, token expiry and rate limits.

## Structure

- `src/lib/policy.ts` status flow, SLA, permissions (pure functions, start here)
- `server/db.ts` schema, constraints, audit triggers
- `server/app.ts` routes, validation, transactions
- `server/auth.ts`, `server/rateLimit.ts` passwords, tokens, throttling
- `server/seedData.ts` fictional demo data
- `src/` React screens: `TicketList`, `TicketView`, `NewTicket`, `AuditPage`, `Login`

## Known limits

- No email notifications, attachments, real-time updates, or SLA pause while waiting on the customer.
- No password reset or email verification. No UI to create staff (API only).
- Rate limits are in memory (single process). Tokens live in localStorage, so an XSS bug would expose them; httpOnly cookies would be safer.
- Search is a simple `LIKE`, not full-text.
- SQLite file on disk: hosts with an ephemeral disk lose data on redeploy.
